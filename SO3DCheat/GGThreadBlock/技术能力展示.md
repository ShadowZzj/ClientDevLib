# SO3D 客户端逆向与自动化系统 —— 技术能力展示

> 一套围绕同一款 32 位 Windows 网游客户端（SO3D Plus，Winlicense 加壳）做的逆向 + 自动化系统。
> 由三个互相配合的子系统组成：注入式功能 DLL、纯协议在线客户端、Web 控制台中间层。
> 三者覆盖了 **二进制逆向、密码学还原、私有网络协议重建、Windows 系统编程、全栈工程化** 五个方向。

---

三个子系统解决的是同一个问题的三个层面：

| 子系统 | 一句话定位 | 核心难点 |
|---|---|---|
| **GGThreadBlock.dll** | 注入到游戏进程的功能 DLL（反保护 + 内存挂 + 借壳） | 加壳延迟解包、GameGuard 对抗、运行时内存补丁 |
| **so3d_online_login** | 脱离游戏客户端、纯协议重放/重建的在线挂机器 | 私有加密链 + 私有协议的完整还原 |
| **GGTB Broker** | 把 N 个游戏实例统一接到一个 Web 面板的中间层 | 多进程编排、命令/状态双向流、业务自动化 |

## 1. GGThreadBlock.dll —— 注入式功能 DLL

### 1.1 大概功能

注入到 `so3dplus.exe` 后承担两类角色：

**A. GameGuard 反保护抑制层**
- Detour `CreateThread`：拦截源自 `GameGuardDll.dll` 的 worker 线程，重定向到 `Sleep(INFINITE)` 的空过程，让保护线程“启动成功但永不工作”。
- Detour `SetWindowsHookExA/W` + `UnhookWindowsHookEx`：返回哨兵 HHOOK，让宿主安装的 `WH_KEYBOARD_LL` 全局键盘钩子“看起来成功、实际不生效”，从而夺回 Win 键 / Alt-Tab 任务切换。
- 一次性把 `NPmsg.dll+0x103D3` 的 `jng` 改 `jmp`，绕过一处检测分支。

**B. 游戏功能模块宿主（ImGui 菜单）**
- 一组可热开关的 `IModule`：移速 / 攻速 / 技能速度 / 全局加速 / 物品无 CD / 攻击距离 / 边攻击边移动 / 自动捡物 / 全威力 / 自动确认 / 自动接受组队 / 原地挂机 / 玩家 ESP / 附近真人守卫（NPG）。
- **NPG（附近真人守卫）** 是一个亮点设计：检测到附近有真实玩家时自动把所有“变态类”模块拍暂停，离开后恢复，降低被举报风险。

**C. LoginBridge（借壳解密桥）** — 见第 2 章，是连接 DLL 与 Python 客户端的关键。

此外附带 `Starter.exe` 批量登录器：读账号列表拉起多个游戏进程，并按分组共享伪造硬件指纹。

### 1.2 技术栈

- **语言**：C++17，静态 CRT（`/MT`），UTF-8 源码，UNICODE
- **Hook 框架**：Microsoft Detours（vendored）
- **渲染/UI**：Dear ImGui + DirectX9，通过 hook `EndScene` 注入菜单
- **构建**：CMake ≥ 3.15，Win32(x86)，MSVC
- **日志/序列化**：spdlog、nlohmann/json
- **其它**：Boost.Locale（Big5↔UTF-8 转换）、自研 `ClientDevLib`（封装 Process/Memory/MD5/D3D9Hook）

### 1.3 逆向思路与工程亮点

1. **对抗加壳的延迟解包（stage-2 触发器）**
   目标是 Winlicense 壳，`DllMain` 时很多代码段尚未解密，直接 detour 会打到错误字节。设计了 `Stage1Trigger`：监听宿主第一次 `DeleteFileA("error.txt")` 作为“解包完成”信号，把真正的 hook（NetLog/HwFpSpoof/DisconnectWatchdog）全部延后到 stage-2 回调里安装。

2. **DllMain 死锁纪律**
   严格约定 `DllMain` 里**只**做 `DisableThreadLibraryCalls + InstallDetour + 起线程`，绝不做文件 IO / spdlog / 重 hook —— 避免 loader lock + registry mutex 死锁。这类约束是踩过坑后沉淀的工程纪律。

3. **特征码扫描 + MD5 缓存**
   所有内存补丁点经 `PatternResolver` 按特征码定位，结果按二进制 MD5 缓存到 `ggtb_pattern_cache.json`；游戏版本一变 MD5 失效自动重扫，避免硬编码地址随版本失效。

4. **IDA 驱动的逆向纪律**
   弄清一个 global/function 含义就立刻在 IDA 里改名加注释，函数偏移、补丁 size、cap 常量统一写在 `CLocalPlayer.h` 顶部并注明出处。

## 2. so3d_online_login —— 纯协议在线客户端（最核心的逆向成果）

> 这是整个系统逆向含金量最高的部分：**完全脱离游戏客户端，用纯 Python 重建了登录 + 游戏的全套私有加密与协议**，可无头登录、批量挂机（钓鱼/摆摊/贩卖/补货/复活/邮寄等）。

### 2.1 大概功能

- 从账号 / 密码**重新生成**登录包（不是抓包重放），完成 `登录 → 计费握手 → 取角色 → 选服 → 进世界` 全流程，并用与真客户端一致的保活包维持在线。
- 支持自动建号、二次登录握手、多账号多线程并发，每账号独立 stop/重连，断线自愈。
- 内置完整挂机业务：自动钓鱼、背包将满自动贩卖、鱼饵不足自动购买、个人摆摊上下架、账号仓库搬运、自动复活回城、自动邮寄金币等。
- 自带 Tkinter GUI + CLI 两套入口，可打包成单 exe（PyInstaller）。

### 2.2 技术栈

- **语言**：Python 3.11，纯标准库 socket / struct / threading / select，外加 `pycryptodome`（Blowfish）
- **架构**：严格分层模块化（import 只允许向下）：
  `runtime → logio/protocol/crypto → tables → config → packets → netio → farm.* → session/selftest → gui → cli`
- **并发模型**：每账号一个 `AccountController`（独立 stop event + socket 集合 + 动作队列），GUI 线程只读 worker 快照、手动动作通过队列投递到 worker 线程执行（保证同一 game socket 不被两个线程同时 `sendall` 撕裂 TCP 帧）。

### 2.3 逆向思路与亮点

这部分是**密码学还原 + 协议重建**的组合拳，分三层剥开：

**① Layer-2：自研 DES + 8 组 XOR，握手协商密钥**
- 登录端口（10002）的报文 = 自研 DES 加密的字段 + 逐连接选定的 XOR 流。
- 直接从 IDA 反汇编 `sub_5CC2E0` / `sub_5CCB60` 把游戏的 **DES 实现（IP / FP / E / P / S 盒 + 16 轮 Feistel 子密钥 `K_ENC`）逐位还原**成 Python（见 `crypto.py`）。
- XOR 密钥不是固定的：服务器在 lobby 握手包里塞了一个 key seed，客户端要**对它做奇偶校验、再取 bit 25..27 解出 8 组密钥中的索引**（`handshake_xor_index`）。这个推导逻辑是从客户端校验代码反出来的，比 fallback 硬编码可靠得多。

**② Layer-1：123.dll 的 VM 化传输层加密 —— 用“借壳”破解**
- 真正的难点在于：正式服在 XOR 之上还套了一层 `123.dll` 的传输加密，且是 **VM（虚拟机）混淆**实现，静态还原成本极高。
- **解法非常工程化**：不去硬啃 VM，而是**把活的游戏进程当成“解密预言机”**。GGThreadBlock.dll 在游戏内开 `\\.\pipe\GGTB_LOGIN_BRIDGE_<pid>` 命名管道，Python 客户端把密文丢给它，DLL 调用游戏自己的 `123.dll` 解密例程拿回明文。
- 配套绕过：123.dll 的解密前有一道 **socket-fd 校验门**（`obf_gateA_socket_fd_check`，比较“收到的 fd”与“CGameClient 对象 +0x10 存的 fd”是否相等）。通过把 `123.dll+0x7560C3` 的 6 字节 `jnz` NOP 掉（`forceDecrypt`），强制解密分支命中，**让任意缓冲都能走通解密**，与具体 socket 解耦。
- 这套“借壳”思路非常能体现 **务实的逆向价值判断**：在 VM 还原（高成本）和借用运行时（低成本、高可靠）之间做了正确取舍。`verify_decrypt_chain.py` 端到端验证 2/2 匹配。

**③ 协议层：逐 opcode 重建游戏语义**
- 用 IDA 对照 send/recv 抓包，把上百个 opcode 的**帧布局逐字节标注**（见 `packets.py`，注释里写满了 `handler sub_XXXXXX@0x...` 的出处与偏移）。例如：
  - 主背包整桶 `511591`：头 4B + 13 装备格 + 192 主背包格×16B + 205 个尾部 u32，内部 slot k → wire slot k+13；
  - 卖货回流 `521054` 的金币藏在 `body+20`（中间夹了一个恒 0 的 u64，必须 `len>=40` 才读得到）；
  - cash 状态 buff 的 type→中文名表，是用 `dump_cash_buffs.py` **直接读在线游戏 GameHUD 的 cash vector** 核实出来的，不是猜的。
- 心跳包这种细节也踩过坑并记录在案：1842 世界服真正的保活是 `411013`（body 8 字节全 0），而不是看起来更像的 `411041`，发错服务器不认。

> 这一章能讲的故事很多：**自研对称密码逐位还原 / 握手密钥推导 / VM 加密的借壳绕过 / 私有协议逐字节重建 / 多账号并发架构** —— 每一条都是独立的硬技能。

## 3. GGTB Broker —— Web 控制台中间层

### 3.1 大概功能

把分散在 N 个游戏进程里的 GGThreadBlock.dll 统一接到一个浏览器面板：
- **实例注册中心**：DLL 主动连过来上报 `hello/identity/status/moneyUpdate` 等帧，Broker 维护在线实例列表（pid、角色名、账号、金币、HP、坐标、地图）。
- **命令下发**：浏览器 `POST /api/command/:pid` → Broker 透传给对应 DLL → DLL 回 `ack`（带 uuid 关联）。
- **20+ 业务自动化管理器**：自动复活、死亡通知、GM 自动应答、金币统计、Buff 守护、摆摊监控、泡点购买、自动组队、自动合成、奖励领取、在线白名单同步等，每个都是独立可销毁的模块。

### 3.2 技术栈

- **后端**：Node 20 + TypeScript，Express + `ws`，命名管道用 `net.createServer` 直接 listen `\\.\pipe\X`
- **前端**：Vue 3 + Element Plus + ECharts + Vite（另保留一套零依赖 `web/app.js` 作为降级 UI）
- **打包**：`@yao-pkg/pkg` 打成单 `ggtb-broker.exe`，前端资源随包

### 3.3 设计亮点

- **协议极简、职责单一**：帧 = `UTF-8 JSON + \n`，Broker 本体只做透传与注册，加新命令只需 DLL 端 `RegisterCommandHandler` + 前端加个表单，**不用改 Broker**。
- **健壮性细节**：同 pid 复连时挤掉残留旧连接（应对游戏被强杀、close 还没到）；`pending` ack 用 uuid + 超时 + 连接关闭统一 reject，不会泄漏 Promise。
- **跨系统协同**：`OnlineWhitelistSync` 等模块把本机在线角色推到远端服务，多台机器之间共享“谁在线”的白名单，支撑 NPG 跨机判断。

## 5. 能力提炼

- **二进制逆向**：IDA/CE 实战，加壳（Winlicense）延迟解包，VM 混淆代码的应对策略。
- **密码学还原**：从反汇编逐位重建私有 DES（IP/FP/S 盒/Feistel），握手密钥推导，Blowfish-CBC 对接。
- **网络协议工程**：完全脱离客户端重建私有二进制协议，上百 opcode 帧布局逐字节标注与重放，TCP 分帧/重组/对齐自愈。
- **Windows 系统编程**：Detours API hook、命名管道 IPC、DLL 注入、D3D9 EndScene hook、loader-lock 安全。
- **C++ / Python / TypeScript 全栈**：C++17 注入 DLL、分层模块化 Python 并发客户端、Node+Vue 全栈控制台。
- **系统设计**：DLL ↔ Broker ↔ Web ↔ Python 客户端四方协同，命令/状态双向流，多进程编排与业务自动化。
- **务实的工程判断**：在“纯静态硬啃”与“借用运行时”之间做正确的成本/可靠性取舍，并用端到端测试验证。
